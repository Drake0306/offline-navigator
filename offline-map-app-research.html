01

The bottom line

If you only read one screen, read this. The most accurate offline result with the least licensing cost comes from a fully open-source stack, wrapped in one cross-platform UI.

Recommended stack

MapLibre + OpenStreetMap/PMTiles + Valhalla

One cross-platform UI driving a native map-rendering and routing core. Everything the app needs to run with no internet after the initial download.

The one decision that needs a prototype first

Every layer above is solid and well-documented except on-device routing. The open-source path to running Valhalla inside a mobile app currently leans on a community build (Rallista/valhalla-mobile) that is self-described as “not yet ready for production.” De-risk this with a one-week spike before committing — and keep Mapbox Navigation SDK in your back pocket as a turnkey commercial fallback for the routing/navigation layer.

Why this stack

  • Genuinely offline. Vector tiles (PMTiles) and routing tiles (Valhalla) are both file-based and read straight from local disk — no tile server, no network calls once downloaded.
  • Accurate. Valhalla ships Meili (hidden-Markov map-matching to snap noisy GPS onto roads) and Odin (turn-by-turn maneuver generation) — the two pieces that make navigation feel “Google-Maps smooth.”
  • Free & unencumbered. MapLibre is BSD-2-Clause, Valhalla is MIT, OSM data is free. No per-request map fees.
  • One UI, both platforms. MapLibre has official React Native and Flutter bindings that render via the same native engine — so you write the screens once.

03

Decision 1 — Cross-platform vs native

You want both Android and iOS. The key question: can you write the UI once and still get native-grade map rendering, routing and GPS accuracy? Yes — and the research confirms it.

The heavy lifting in a navigation app (map rendering, routing, location) is native no matter which framework you choose. A cross-platform layer mainly owns the screens: search, the region download manager, the trip planner, and the on-screen navigation chrome. Both major cross-platform frameworks can render through the same native MapLibre engine and call into a native routing/location core.

How the UI talks to native Verified · 3-0

  • React Native bridges via JSI / TurboModules — a C++ layer that lets JS call native synchronously when needed (the default architecture since RN 0.76, late 2024).
  • Flutter bridges via MethodChannel — documented async messaging between Dart and Kotlin/Swift.

Map rendering is truly native Verified · 3-0

  • RN: the official @maplibre/maplibre-react-native renders with MapLibre Native for Android & iOS — not a WebView.
  • Flutter: flutter-maplibre (officially announced by MapLibre, Sept 2024) uses maplibre-native on mobile.
My recommendation Synthesis

Lead with Flutter (or React Native if your team lives in JS/TS), with a thin native module for routing + location. A navigation app is rendering- and animation-heavy — smooth 60 fps map-follow, a rotating pointer, a live speedometer overlay — which plays to Flutter's rendering consistency, and flutter-maplibre is MapLibre's officially blessed plugin. React Native is an equally defensible #2 (largest plugin ecosystem, official MapLibre binding, performant JSI bridge). The research confirmed both are viable; it did not benchmark one against the other — the choice should weigh your team's skills.

Go fully native (Kotlin + Swift) only if you want maximum control over GPS/sensor fusion and the routing-core integration and are willing to pay for two separate UI codebases. It's the lowest integration risk for the routing core, at the highest UI cost.

04

The stack, layer by layer

Each layer, what it does, the license, and the confidence level behind the recommendation.

① Map rendering — MapLibre Native BSD-2-Clause · Free Verified · 3-0

The open-source successor to the last freely-licensed Mapbox GL Native, with native SDKs for Android and iOS sharing one C++ rendering core. It renders vector tiles (crisp at any zoom, restyleable, smaller than raster), supports camera pitch/tilt for the 2.5D look (the Flutter plugin exposes initPitch — max 60 on mobile — plus minPitch/maxPitch and bearing, and ships a “tilted and rotated map” preview), and supports symbol layers with custom, rotatable icons — exactly what a swappable directional pointer needs. Exact API names differ across the RN/Flutter/native bindings — confirm against the version you pick.

② Map data & tiles — OpenStreetMap → PMTiles via Planetiler Free / OSS Verified · 3-0

PMTiles is a single-file archive that holds a whole pyramid of tiles and is read directly from local disk (or via HTTP range requests) with no tile server — ideal for bundling a downloaded region. Planetiler turns raw OpenStreetMap data into vector tiles fast (it can build the entire planet in a few hours on one machine) and outputs PMTiles or MBTiles. Region selection is a build-time step: --area=<named Geofabrik region> generates tiles for that extract — so you pre-cut packs per offered region rather than from an arbitrary on-device bounding box.

Licensing note

OpenStreetMap data is licensed ODbL. You must attribute OSM and respect its share-alike terms for the data. This is normal for OSM-based apps but worth designing the attribution UI for from day one.

③ Routing — Valhalla on-device MIT Verified · 3-0 Mobile packaging immature

Valhalla is an MIT-licensed routing engine with a tiled, hierarchical data structure explicitly designed for “a small memory footprint on memory-constrained devices… regional extracts and partial updates” — precisely the mechanism for offline, on-device routing of user-selected areas. It is multimodal (car, bike, pedestrian and more), generates turn-by-turn instructions via Odin, and snaps GPS to roads via Meili map-matching. Re-routing is a matter of re-requesting a route from the current snapped position.

The risk to plan around Verified · 3-0

Running Valhalla inside the app currently relies on the community Rallista/valhalla-mobile packaging (an iOS Swift Package / ValhallaCore.xcframework, iOS 13+, and an Android Maven Central com.rallista:valhalla AAR). It genuinely runs offline with no runtime server — but the README says it is “not yet ready for production,” currently exposes only the route() function, and the upstream Valhalla project ships no first-party mobile binaries (its packaging discussion is still open). Treat on-device Valhalla as the item to validate first. Motorbike / two-wheeler isn't a guaranteed stock costing model — plan to author and validate a tuned custom profile.

④ Offline search — SQLite FTS5 over an OSM index Open question Synthesis

There's no single dominant turnkey offline-geocoding library for mobile, so most teams build a custom index: extract named features (POIs, streets, addresses) from the OSM data for each downloaded region into a SQLite database with the FTS5 full-text extension, then query it for instant offline search-as-you-type. This sits outside the verified findings — the research flagged offline search as under-addressed — so budget engineering time and prototype it. Reference points worth studying: Photon (offline-capable OSM geocoder) and Organic Maps (a shipping offline OSM app with on-device search).

⑤ Location & accuracy — Fused Location + CoreLocation Std. practice

On Android, FusedLocationProviderClient (Google Play services) is the recommended high-accuracy, battery-aware API; use PRIORITY_HIGH_ACCURACY for navigation. On iOS, CoreLocation is the equivalent with configurable desired accuracy. Layer on sensor fusion (compass/gyroscope) for a stable heading, light smoothing/Kalman-style filtering, and Valhalla's Meili map-matching to keep the pointer glued to the road. These are documented platform standards rather than findings from this research pass — the specific accuracy techniques (Kalman tuning, sensor-fused heading) are an open question to settle in the prototype.

07

How each feature is built

Mapping your requirements to concrete mechanisms.

Downloadable regions & the download manager

Pre-build per-region packs (PMTiles map + Valhalla routing tiles + SQLite search DB) and host them statically. The in-app download manager fetches a selected region once over the internet, verifies it, and stores it locally. This is the only component that ever needs a network.

Offline search

Query the region's SQLite FTS5 index for search-as-you-type over place names, POIs and addresses. Results feed straight into the trip planner as the “to” point. Open question — the exact offline-search approach wasn't settled by the research; prototype it early.

Trip planning A→B for 4 modes

Valhalla computes the route on-device for the selected profile (car / pedestrian / bicycle / motorbike). Car, bike and foot are first-class; motorbike/two-wheeler will likely need a tuned custom profile — plan to author and validate it.

Turn-by-turn (no voice in v1)

Odin produces the maneuver list (turn left, continue, roundabout exit, distances). The UI renders these as an instruction banner with the next maneuver and distance-to-it, advancing as you progress. Off-route detection compares the snapped position to the route geometry and triggers a Valhalla re-route. Voice (Android/iOS TTS reading Odin's text) is a clean later add-on — the instruction text already exists.

Live GPS pointer, vehicle icons, speedometer, 2.5D

Render the user as a MapLibre symbol with a custom icon rotated to the heading — a directional arrow by default, swappable to a car/bike sprite when navigating. The speedometer reads speed from the location fix (a simple overlay widget). The 2.5D effect is the MapLibre camera's pitch/tilt with a follow-camera that tracks the pointer. Synthesis — the tilt/symbol capability is verified; this exact UI assembly is a recommended pattern to confirm against your binding.

Storage & data size — estimates to validate, not measured Open question

The research did not benchmark sizes; measure these in your prototype. As rough industry ballparks to plan around: a metro-area vector tile pack is typically tens–low-hundreds of MB; a whole country can be hundreds of MB to several GB; Valhalla routing tiles for a region add a comparable order of magnitude.

Plan for: Android scoped storage (app-specific external dir, optional SD-card via the Storage Access Framework) and iOS app-sandbox storage with downloaded packs flagged so the OS handles backup/purge sensibly.

08

Open-source path vs Mapbox

You asked to prefer open-source where it doesn't hurt accuracy. Here's the honest trade.

Open-source · MapLibre + OSM/PMTiles + Valhalla

Pros

  • $0 licensing; no per-request fees
  • Full control over data, tiles and storage
  • Accuracy parity — Meili + Odin are strong
  • No vendor lock-in

Cons

  • On-device Valhalla packaging is immature (esp. iOS)
  • You build the search index & download pipeline
  • More integration engineering up front

Commercial · Mapbox (Maps + Navigation SDK v3)

Pros

  • Turnkey offline turn-by-turn + automatic re-routing
  • TileStore manages routing and map tiles offline
  • Lower engineering risk; faster to a working nav app

Cons

  • Proprietary; usage-based cost that scales with users
  • Vendor lock-in on the navigation layer
  • Less control over data & storage
Recommendation Synthesis

Commit to the open-source stack, but treat Mapbox as a pre-qualified fallback specifically for the routing/navigation layer. If the Valhalla-on-device spike (see Roadmap, Phase 0) doesn't reach the reliability bar, swapping in Mapbox Navigation buys a turnkey path without re-architecting the rest. A pragmatic hybrid is also valid: MapLibre + OSM for rendering (free), Mapbox only for navigation.

Recommended roadmap

De-risk first, then build outward from a working offline map.

PHASE 0 De-risk spikes do this first

Two throwaway prototypes on both Android & iOS: (a) MapLibre rendering a local PMTiles pack; (b) Valhalla computing a route on-device from local tiles. Decide open-source vs Mapbox-fallback based on the result.

PHASE 1 Offline map + region downloads

Map screen with pan/zoom and 2.5D tilt, plus the region download manager reading/writing local packs.

PHASE 2 Offline search

SQLite FTS5 index + search-as-you-type over downloaded regions.

PHASE 3 Trip planning A→B

Valhalla routing for all four profiles; draw the route line and summary (distance/ETA).

PHASE 4 Live tracking

High-accuracy location, map-matched directional pointer, swappable vehicle icons, follow-camera, speedometer overlay.

PHASE 5 Full turn-by-turn

Odin maneuver banner, route-progress, off-route detection & automatic re-routing.

LATER Optional add-ons

Voice guidance (TTS over Odin text), richer 3D, lane guidance, traffic — none required for v1.

The research's own open questions
  • Best offline geocoding/place-search approach for OSM on-device (Photon offline, SQLite FTS, engine-built-in search, or Mapbox offline search) and its cross-platform performance within a downloaded region.
  • Concrete GPS/location accuracy practice for a smooth pointer: Fused vs raw GPS, iOS CoreLocation settings, compass/gyro fusion for heading, Kalman filtering vs relying on Meili map-matching.
  • How GraphHopper/OSRM/BRouter compare to Valhalla for on-device offline turn-by-turn with all four profiles (esp. a real motorbike costing model) on both iOS and Android.
